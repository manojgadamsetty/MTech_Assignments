ASR 1 Utility Tree - Availability and Reliability

Why this is architecturally significant: Ride-booking is revenue-critical and safety-sensitive. If dispatch fails during peaks, users churn immediately and operations collapse.

Utility Tree Path Concrete Scenario Priority Architectural Impact
Utility -> Availability -> Fault Tolerance During a zone outage, 95% of new ride requests are still accepted and dispatched within 60 seconds. (H, H) Requires active-active deployment, retries, idempotency, and health-aware routing.
Utility -> Availability -> Recoverability After broker/database node failure, service auto-recovers without manual restart and no confirmed booking is lost. (H, H) Forces durable events, transactional outbox, and exactly-once business semantics.

Utility Tree Path Concrete Scenario Priority Architectural Impact

Slide 4

Tactics for ASR 1 - Availability and Reliability

Recommended Tactics

  • Redundancy: Active-active across two regions; global traffic manager routes to healthy region.
  • Health-based routing: Gateway routes only to healthy pods using readiness probes.
  • Idempotent booking API: Client sends request-id so retries do not duplicate rides.
  • Transactional outbox: Booking DB commit and event publish stay consistent.
  • Back-pressure and queueing: Kafka buffers dispatch tasks during spikes.
  • Circuit breaker: Fallback when pricing or maps service is degraded.

What, Tool, and How

What to protect: booking acceptance, driver assignment, trip state.

Tools: Kubernetes + HPA, AWS ALB/Route53, Kafka, PostgreSQL, Redis, Resilience4j.

How it works: retryable requests hit API Gateway, Booking Service writes booking + outbox row, event consumer sends to Kafka, Dispatch Service consumes and assigns driver. On service failure, retries + fallback path preserve user flow.

Expected Result

New requests keep flowing through partial failures; no loss of confirmed bookings.

Slide 5

Tactics for ASR 2 - Performance and Low Latency

Recommended Tactics

  • Geospatial indexing: Nearby drivers in Redis GEO index.
  • Cache-aside: hot entities (driver status, city config, ETA seeds) in Redis.
  • Asynchronous pipelines: location updates on Kafka stream.
  • Regional sharding: partition trips by city/zone for locality.
  • Bulkhead isolation: independent thread pools for ETA, pricing, and dispatch.
  • Timeout budget: strict p95 timeout per downstream call.

What, Tool, and How

What to cache: active driver coordinates, demand heatmaps, route estimates, policy metadata.

Tools: Redis Cluster, Kafka, gRPC for low-latency internal calls, OpenTelemetry for tracing.

How it works: Driver App pushes location every few seconds, Location Service updates Redis GEO + stream. Dispatch queries nearest drivers from memory, then confirms with Booking Service over gRPC for faster match decision.

Expected Result

Fast, predictable matching under peak traffic with reduced database load.

Slide 6

Tactics for ASR 3 - Security and Privacy

Recommended Tactics

  • Tokenization: store payment token only; payment gateway keeps PAN data.
  • Encryption: TLS 1.3 in transit, AES-256 for PII at rest.
  • Zero-trust service auth: mTLS between services via service mesh.
  • Policy-based access control: scoped JWT + role checks per endpoint.
  • Auditability: immutable audit events for admin and support actions.
  • Fraud/rate controls: per-device and per-account anomaly rules.

What, Tool, and How

What to protect: rider profile, phone number, live location, payment operations.

Tools: API Gateway with OAuth2, Vault/KMS, Istio mTLS, WAF, SIEM.

How it works: Gateway validates token and scopes, services decrypt only needed fields using KMS envelope keys, all privileged reads are emitted as signed audit events to SIEM.

Expected Result

PCI and privacy exposure reduced with strong traceability of sensitive operations.

Architecture Pattern 1 - Microservices with API Gateway

Where it is used

  • Gateway fronts all client traffic and centralizes auth, throttling, and request routing.
  • Domain services are separated by business capability: Booking, Dispatch, Trip, Payment, Notification.

Why this pattern fits

  • Independent scaling: Dispatch and Location scale far more than profile services.
  • Independent deployment: teams release services without full-system redeploy.
  • Fault isolation: failure in Notification does not block core booking path.

Trade-off handled

Operational complexity is mitigated using standardized CI/CD templates, observability, and service contracts.

Slide 12

Architecture Pattern 2 - Event-Driven Architecture (with Saga Style)

Where it is used

  • Ride lifecycle changes are published as events (RideCreated, DriverAssigned, TripCompleted).
  • Downstream services consume events asynchronously for dispatch, notifications, analytics, and billing.

Why this pattern fits

  • Loose coupling: producers do not depend on consumers being online.
  • High throughput: events buffer burst traffic and smooth load.
  • Business traceability: lifecycle transitions become auditable event history.

Trade-off handled

Eventual consistency is managed through idempotent consumers, retries, and compensation actions for failed payment or dispatch steps.
